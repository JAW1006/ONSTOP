# 데이유즈 예약 (예약 요청 · 요청 내역)

> 상태: **초안 — 사용자 확인 전(구현 시작 안 함)** · 최종 수정 2026-10-16
> 레거시: `Booking`(app/index.html 1015–1107줄), `Confirm`(1115–1180줄)
> 공식: [dayuse-pricing](../../formulas/dayuse-pricing.md)(A9 `DayuseOffer`) · [time-fit](../../formulas/time-fit.md)(A6 순차 경로) · [time-safe](../../formulas/time-safe.md)
> 관련 결정: [ADR-0003 인증](../../decisions/ADR-0003-auth.md)(비회원, 제안) · [ADR-0004 결제](../../decisions/ADR-0004-payment.md)(제안 — 결제 없음) · [legal-checklist](../../legal-checklist.md) 0장

## 목적
환승객이 데이유즈 숙소 이용을 **호텔에 요청**하고, 호텔이 확인하면 확정되는 첫 예약 흐름. **결제는 하지 않는다**(ADR-0004 결정 전). 앱은 체크인 시각과 상품(시간 블록)을 고르게 돕고, 그 선택이 연결편 복귀 시각과 맞는지 보여준다.

레거시는 "결제하기 → 예약 완료(가짜 QR)"였다. 새 화면은 **"예약 요청 → 호텔 확인"**이며, 확정 전에는 "예약 완료"라고 쓰지 않는다.

## 진입/이탈
| 항목 | 내용 |
|---|---|
| 라우트 | `/booking/:roomId`(요청 작성), `/bookings`(요청 내역·상태) — 지금은 자리표시 화면 |
| 진입 ① | 저장된 코스 "이 숙소로 예약하기" → 저장된 코스의 숙소·장소·**실제 경로** 사용 |
| 진입 ② | 홈 데이유즈 카드(`RoomCard`)·"더보기" → 저장된 코스 없이 숙소만. 이동시간은 근사 |
| 이탈 | 요청 보내기 → 요청 완료 화면(`/bookings/:requestId` 또는 `/bookings` 맨 위) · 뒤로 → 이전 화면 · "코스 만들기" → `/course`(숙소 선택된 상태) |
| 외출 불가 | 화면은 열리지만 이유 표시 + 요청 버튼 비활성(코스 화면과 같은 규칙) |
| 온보딩 전 | 온보딩 가드(기존 규칙)로 `/onboarding` |
| 잘못된 `roomId` | "숙소를 찾을 수 없어요" + 홈으로 |

## 구성 — 요청 작성 `/booking/:roomId` (위→아래)
| # | 블록 | 내용 |
|---|---|---|
| 1 | 헤더 | "데이유즈 예약 요청" + 뒤로 |
| 2 | 숙소 카드 | 사진(허락 확인 전에는 **사진 없는 표시** — legal 0-1) · 이름 · 공항에서 N분(근사면 "약") · 포함 서비스(`offer.includes`, 없으면 표시 안 함) |
| 3 | 외출≠입국 안내 | "입국 가능 여부(국적·비자·환승 조건)는 TimeStay가 확인하지 않아요" 한 줄 + 공식 안내 링크 — 문구·위치는 legal 0-2 안 A/B 결정에 따름 |
| 4 | 체크인 시각 | "숙소까지 이동시간 고려 시 HH:MM 이후" + 30분 간격 후보 6개(`checkInSlots`). 진입 ①은 저장된 코스의 체크인 시각(실제 공항→호텔 구간) 기준, 진입 ②는 근사 기준이며 "약" 표기. 고른 상품의 `startWindow` 밖이면 그 슬롯은 비활성 + 이유 |
| 5 | 상품(시간 블록) | 호텔 가격표 `offer.products` **그대로**(빈 블록·불규칙 가격 허용) — "3시간 ₩50,000" 같은 칩. 부가세 포함 여부 표시. 조건(`conditions`) 있으면 칩 아래 작은 글씨. 기본 선택: 복귀 전까지 들어가는 가장 긴 상품(`defaultTier` 규칙) |
| 5′ | 가격 없음 | `offer`가 없거나 `products`가 비면 상품 칩 대신 **"가격 확인 중"** 카드(호텔 데이터 대기) + 요청 버튼 비활성. 레거시 계산식(`roomHourTiers`)은 쓰지 않는다 |
| 6 | 시간 맞춤 확인 | 체크인–체크아웃 막대와 복귀 기준 시각 비교. 넘치면 빨간 경고(레거시 `checkoutPastReturn` 문구 재사용 검토) — 기준 시각은 **B1 결정**에 따름 |
| 7 | 포함 일정 | 진입 ①이면 저장된 코스 장소 N개(이름·체류) — 레거시와 같음. 진입 ②면 "코스를 만들면 복귀 시각까지 함께 계산해요" + 코스 만들기 버튼 |
| 8 | 요청 내용 | 상품 · 체크인–체크아웃 · **예상 금액**(호텔 가격표 기준, "결제는 호텔 확인 후 안내" — 결제 방식은 ADR-0004 결정 후) · 연장·취소·노쇼 규정(`offer.extension`/`cancellation`/`noShow`, 없으면 "호텔 확인 후 안내") |
| 9 | 연락처 | 이름 + 이메일(필수, ADR-0003 비회원 제안). 이메일은 두 번 입력 또는 확인 단계(오입력 대비). 선택: 메신저 연락처(종류 미정). **여권 정보는 받지 않는다** |
| 10 | 동의 | 개인정보 수집·제3자(호텔) 제공 동의, 이용 조건(계산은 참고용, 탑승 책임은 이용자) — 문구는 legal 확인 전 초안 |
| 11 | 버튼 | **"예약 요청 보내기"**(결제 아님). 아래 "호텔이 확인하면 이메일로 알려드려요 · 보통 N분 안에 답해요"(`requestResponse.typicalMinutes`, 없으면 문장 생략) |

## 구성 — 요청 내역·상태 `/bookings`
| # | 블록 | 내용 |
|---|---|---|
| 1 | 헤더 | "내 예약" |
| 2 | 요청 카드(최신 위) | 상태 배지 · 숙소 · 상품 · 체크인–체크아웃 · 예상 금액 · 요청번호 |
| 3 | 상태 | **요청됨**(회색·대기 아이콘, "호텔 확인 중") / **확정**(초록, "호텔이 확인했어요" + 체크인 안내) / **거절**(빨강, 사유 있으면 표시 + "다른 숙소 보기") — 그 외(취소·만료)는 B5 |
| 4 | 확정 후 | 복귀 카운트다운·캘린더 추가(ADR-0006 1단계)는 이 카드에 붙인다 — 별도 구현 단계 |
| 5 | 비어 있음 | "아직 예약 요청이 없어요" + "숙소 보러가기"(레거시 문구 재사용) |
| 6 | 가짜 QR | **넣지 않는다**(레거시 데모 QR 삭제). 확정 시 호텔 체크인에 필요한 것은 인터뷰 2장 결과에 따름 |

## 빈/오류/로딩 상태
| 상황 | 처리 |
|---|---|
| 항공편 조회 중 | 체크인 후보·경고 자리에 로딩 표시, 요청 버튼 비활성 |
| 항공편 조회 실패 | Time-Safe와 같은 오류 문구 + 다시 시도, 요청 버튼 비활성 |
| 저장된 코스 경로 조회 실패 | 근사로 계산 + "약" 표기(저장된 코스 화면과 같은 규칙) |
| 상품 없음 | 5′ "가격 확인 중" |
| 모든 슬롯이 `startWindow` 밖 | "이 숙소는 지금 시간대에 이용할 수 없어요" + 다른 숙소 보기 |
| 어떤 상품도 복귀 전까지 안 들어감 | 가장 짧은 상품 기본 선택 + 경고(레거시와 같음). 요청은 **B3** 결정에 따름 |
| 요청 전송 실패 | 입력값 유지 + "보내지 못했어요. 다시 시도해 주세요" |
| 이메일 형식 오류 | 필드 아래 오류 문구 |

## 레거시와 다르게 하는 점
| 항목 | 레거시 | 새 화면 | 근거 |
|---|---|---|---|
| 흐름 | 결제하기 → 예약 완료 | 예약 요청 → 호텔 확인(요청됨/확정/거절) | 2026-10-16 결정, ADR-0004 제안 |
| 가격 | 기본가 + 계산식(`TIER_STEP_RATIO`) | 호텔 가격표 그대로, 없으면 "가격 확인 중" | A9 |
| 체크인 기준 이동시간 | 정적 `move` | 저장된 코스의 실제 경로(없으면 근사) | A10 |
| 완료 화면 | "예약 완료" + 가짜 QR + "알림 켜짐" | 상태 배지, QR 없음, 알림 문구 없음 | 기능 없는 표시 제거(알림 문구 삭제와 같은 원칙) |
| 결제 수단 문구 | "간편결제 · Alipay · WeChat Pay · Card" | 표시하지 않음 | 결제 없음 |
| 연락처 | 없음 | 이름·이메일 | ADR-0003 |
| 외출≠입국 | 없음 | 안내 한 줄 + 링크 | legal 0-2 |
| 사진 | 레거시 사진 | 허락 확인 전 사진 없는 표시 | legal 0-1 |

## 결정 필요 (구현 전에 답이 필요한 것)
| # | 질문 | 선택지 | 제안 |
|---|---|---|---|
| **B1** | 데이유즈 체크아웃 기준은? 순차 경로(A6)는 공항→**호텔**→장소들→공항이라, 코스상 호텔에 머무는 시간이 0이고 장소에서 바로 공항으로 간다. 그런데 상품은 "샤워·휴식·**짐보관**" 포함이라 짐을 찾으러 호텔에 돌아와야 할 수 있다 | (a) 레거시처럼 **공항 복귀 목표 시각**과만 비교(코스와 무관) · (b) 코스에 **호텔 복귀**를 넣는다: 공항→호텔→장소들→**호텔**→공항(A6 변경, 공식 md 수정 필요) · (c) 체크아웃 = 호텔 출발 시각(짐 들고 나감, 데이유즈는 짐 맡기기 전 휴식만) | 정하지 않음 — **사용자 결정 필요**(공식과 레거시가 어긋나는 지점). (b)가 실제 이용과 가장 가깝지만 코스 계산·테스트가 바뀐다 |
| B2 | 진입 ②(코스 없이 숙소만)도 요청을 허용? | 허용(근사 기준, "약") / 코스 저장 후에만 | 허용 + 코스 만들기 권유 |
| B3 | 복귀 시각을 넘는 상품도 요청 가능? | 경고만(레거시) / 막기 | 경고 + 확인 체크("일찍 나와야 해요") |
| B4 | 연락처 항목 | 이메일만 / 이메일 + 메신저(WhatsApp·LINE·WeChat 등) / 전화 | 이메일 필수, 메신저는 인터뷰 2장 답 후 |
| B5 | 상태 종류 | 요청됨·확정·거절만 / + 취소(사용자)·만료(호텔 무응답) | 첫 버전 3개 + 만료(응답 기한은 `requestResponse` 기준) — 기한 값 미정 |
| B6 | DB·서버 전에 화면만 먼저 만들지 | 화면 + 메모리 저장(데모 표시) / DB 결정 후 한 번에 | 화면 먼저(domain·UI 테스트로 고정) 후 서버 연결 |
| B7 | 외출≠입국 안내 방식 | legal 0-2 안 A(고정 안내) / B(확인 체크) | A — 요청 버튼 위에도 한 번 더 |
| B8 | 복수 요청 | 같은 날 숙소 여러 곳에 동시 요청 허용? | 1건만(호텔 부담·노쇼 방지) — 인터뷰 4장 확인 |
